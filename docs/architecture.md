# Архитектура

## Устройство

```
клиент ─HTTPS─▶ Caddy ─┬─▶ web #1 (gunicorn: процессы × 4 потока) ─┬─▶ PostgreSQL
                       ├─▶ web #2                                   └─▶ Redis (лимиты)
                       └─▶ web #N
migrate       одноразовый контейнер: manage.py migrate до старта web
flush-tokens  раз в сутки удаляет истёкшие refresh-токены
```

- `config/` — настройки из переменных окружения, URL, точки входа WSGI/ASGI.
- `core/` — общий код приложения: пагинация, троттлинг, health-check, метрики, request id,
  генерация OpenAPI, операции миграций.
- `apps/accounts/` — пользователь, регистрация, JWT.
- `apps/tasks/` — задачи, комментарии, права, фильтры, management-команды.

`web` не хранит состояния и сам не мигрирует, поэтому реплик может быть сколько угодно:
`docker compose up -d --scale web=N`. Caddy находит реплики через DNS Docker и балансирует
`least_conn`.

## Решения по API

- **Списки задач и комментариев — курсорная пагинация** по `(created_at, id)`: ответ
  `{"next", "previous", "results"}`, без `count`. Любая страница — range-scan индекса;
  `OFFSET` и `COUNT(*)` замедляются с ростом таблицы. Порядок фиксирован: задачи — новые
  сначала, комментарии — старые сначала; `?ordering=` нет, курсор стабилен только на
  неизменном ключе. Размер страницы 20, `page_size` до 100. Пользователи — постранично
  (`page`, `count`).
- **Access-токен живёт 15 минут**: его нельзя отозвать.
- **Refresh-токен одноразовый**: `/api/auth/token/refresh/` возвращает новую пару и отзывает
  старый токен, `/api/auth/token/blacklist/` отзывает текущий (выход). Refresh живёт 7 дней.
- **Регистрация не раскрывает занятые имена**: для занятого имени — `400
  {"non_field_errors": ["Registration failed."]}` после всех остальных проверок и с тем же
  хешированием пароля, что и при создании. Ошибки формата указывают поле. Ответ `201` для
  свободного имени всё равно отличается; перебор ограничен лимитом `auth`.
- **Ошибки** — в формате DRF: `{"поле": ["сообщение"]}` для `400`, `{"detail": "…"}` для
  остальных. Коды `400/401/403/404/429` описаны в схеме OpenAPI для каждой операции.
- **Права.** Читать и создавать может любой вошедший: это общая доска одной команды.
  Менять, удалять и назначать задачу — только автор; `complete`/`reopen` — автор или
  исполнитель; комментарий меняет и удаляет только его автор. Чужой объект — `403`,
  несуществующий — `404`.
- **Ограничения полей**: `title` до 255 символов, `description` до 10 000, комментарий до
  2 000, пароль от 10 символов.

## Конкурентность

`complete` и `reopen` блокируют строку задачи (`SELECT … FOR UPDATE`) и проверяют статус
под блокировкой: из двух одновременных `complete` один получит `200`, другой — `400`.
Refresh и logout так же блокируют строку refresh-токена: из двух запросов с одним токеном
новую пару получит один, второй — `401`. `PUT`/`PATCH` работают по принципу «последняя
запись побеждает»; `completed_at` всегда согласован со статусом (`Task.save()`). Тесты гонок
(`tests/test_concurrency.py`) идут на PostgreSQL.

## Счётчик комментариев

`Task.comments_count` хранится в задаче, чтобы список не считал комментарии. Он меняется
атомарным `UPDATE … SET comments_count = comments_count ± N` в транзакции комментария.
Вычитается число строк, которые `DELETE` действительно удалил, поэтому комментарий,
удалённый двумя запросами сразу, вычитается один раз. Массовое удаление на PostgreSQL —
один запрос `DELETE … RETURNING` с `UPDATE` задач при любом числе задач. Удаление задачи
стирает её комментарии одним `DELETE`, удаление пользователя вычитает его комментарии на
чужих задачах одним `UPDATE`. Полное сохранение задачи счётчик не перезаписывает.
`reconcile_comments_count` пересчитывает счётчики после релиза, см.
[operations.md](operations.md#обновление).

## Индексы и запросы

- Список задач, фильтры по исполнителю и автору — составные индексы в порядке курсора;
  они же заменяют индексы внешних ключей.
- Комментарии задачи — индекс `(task, created_at, id)`: страница без сортировки.
- Поиск (`icontains` по названию и описанию) — trigram-индексы GIN на PostgreSQL.
- Число SQL-запросов каждого list/retrieve зафиксировано тестами
  (`tests/test_query_counts.py`).
- `statement_timeout` 5 с на соединениях приложения: зависший запрос не держит поток.
- Индексы на существующих таблицах строятся `CONCURRENTLY` (`core/migration_operations.py`),
  тест не пропустит обычный `AddIndex` в новой миграции.

## Троттлинг

| Лимит | Ключ | Эндпоинты |
|---|---|---|
| `anon` 100/час | IP | все без токена |
| `user` 1000/час | пользователь | все с токеном |
| `auth` 10/мин | IP | регистрация, токен, refresh, logout |
| `auth_account_ip` 10/час | имя пользователя и IP | выдача токена |
| `auth_account` 100/час | имя пользователя | выдача токена |

Счётчики лежат в Redis. Выдача токена проверяет лимиты по порядку и останавливается на
первом отказе, поэтому попытки, отклонённые по адресу, не расходуют общий лимит аккаунта:
с одного адреса владельца не заблокировать. `auth_account` страхует от подбора с многих
адресов; его достижение пишет `WARNING Account throttled` с sha256 имени пользователя.
Без Redis общие лимиты пропускают запросы, лимиты входа считаются в памяти процесса.

## Безопасность

- TLS и HSTS в Caddy. CSP разрешает только свои скрипты, без инлайна: Swagger UI и Redoc
  отдаются из статики.
- Caddy перезаписывает `X-Forwarded-For`, Django доверяет ровно одному прокси
  (`NUM_PROXIES=1`).
- Аутентификация API — только JWT. Админка выключена в продакшене: у её входа нет лимита.
- `/metrics` отдаётся только адресам частной сети, снаружи Caddy отвечает `404`.
- Sentry без персональных данных. Образ: non-root, только wheels с проверкой хешей.
- CI: ruff, тесты на PostgreSQL, `check --deploy`, pip-audit, bandit, gitleaks по истории,
  Trivy по образу, сборка стека с двумя репликами и smoke-тест через Caddy.

## Масштабирование

Одна реплика `web` на 2 vCPU держит около 70 запросов/с, дальше упирается в CPU
([load-testing.md](load-testing.md)). Пропускная способность растёт репликами и ядрами.
Каждый поток gunicorn держит постоянное соединение с БД: `реплики × процессы × потоки`
(`N × 4 × 4`) укладываются в `max_connections=100` до ~5 реплик. Дальше нужен PgBouncer в
режиме `transaction`: `statement_timeout` тогда задаётся через
`ALTER ROLE … SET statement_timeout` (стартовый параметр `options` PgBouncer не передаёт),
`DISABLE_SERVER_SIDE_CURSORS=True`, `CONN_MAX_AGE=0`. За пределы одного хоста: управляемые
PostgreSQL и Redis, тот же образ на нескольких машинах, `migrate` — шаг релиза.
